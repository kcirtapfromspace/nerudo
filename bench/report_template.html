Nerudo Contention Bench

Each of N agents lands K changes into one shared trunk. Every configuration runs the same seeded workload with the same simulated CI. Only the coordination differs: the VCS client, the forge, or the sequencer.

Inside the sequencer

The sequencer lands changes in batches whose footprints don't overlap and runs CI once per batch. Batch size is the lever. It's capped at 16, and the hottest exclusive target limits it no matter how many agents are waiting.

Can models do the review?

A hand-built corpus of changes to a small ledger package, each against a human-written Intent. Some are clean. The rest carry one planted defect, and every one of them passes the test suite. Each change goes through the deterministic gates and then four reviewer models. The routing policies below are scored from the same recorded verdicts.

jj workspaces lose landings silently

Workspaces share one repo, so they share its record of where main@origin is. When agent A pushes, B's lease refreshes too, and B's next push moves the remote branch sideways and drops A's commit. There is no error.

  bookmark: main [move forward from 952bbfbc6de6 to a1cfcc6dcce3]   # A
  bookmark: main [move sideways from a1cfcc6dcce3 to 145fbcc8d400]  # B, accepted
$ git log --oneline main
145fbcc B's change
952bbfb base                                                     # A is gone
jj 0.44.0 · two workspaces, one repo, by hand ·

jj's guard wedges every agent

Two concurrent bookmark set calls leave main conflicted. Without --allow-backwards, every later set is refused, so all agents spin. Before the harness used the workaround below, one 8-agent run logged 5,817 op-log reconciles and 4 pushes in 12 minutes. The hint jj prints is the flag that causes the silent loss above.

Error: Refusing to move bookmark backwards or sideways: main
Hint: Use --allow-backwards to allow it.
harness workaround: snap the bookmark to main@origin first, then move it forward

git worktrees fight over shared refs

Worktrees separate the checkout but not the remote-tracking refs, the stash, or the config. Twelve worktrees fetching at once: 11 failed. One agent's stash is visible to every other.

error: cannot lock ref 'refs/remotes/origin/main': is at <sha> but expected <sha>   ×11

Compare-and-swap is correct, and wasteful

Forty writers race on update-ref main new old. One wins and 39 must regenerate and retest. Without the old-value check, all 40 succeed and 39 commits vanish without a word.

Forgejo's merge ignores merge=union

With CHANGELOG.md merge=union in .gitattributes, local git merges two appends cleanly. Forgejo's server-side merge marks the second PR unmergeable and refuses it. That's why PR-merge needed hundreds of conflict resolutions at 32 agents: about half of all changes append to the changelog.

$ git merge f/b            # local, union driver
  merges clean
forgejo PR b mergeable=False   (polled for 18 s after PR a merged)
POST /pulls/2/merge -> HTTP 405 {"message":"Please try again later"}
Forgejo 16.0.5 · GitHub not tested for this

Method and caveats

  • Workload. 40 targets with Zipf(1.1) popularity. Every change edits one line of one target and adds a unique marker file. Of each change: 50% append to CHANGELOG.md, 30% add a dependency (which rewrites deps.lock, whose digest header makes lockfile edits conflict), and 20% add a migration. The specs are seeded, so every configuration gets identical changes.
  • Agents. A retry regenerates the change on the new trunk; it never rebases text. Simulated generation takes 0.2 s and CI takes s per run. "Merge without retest" resolves conflicts the way an agent would: regenerate the lockfile and keep its own edit. It never re-runs CI.
  • Baselines get their best configuration. CHANGELOG.md merge=union is set in .gitattributes, fetches retry on lock errors with backoff, and jj agents use the careful bookmark recipe. GitHub's merge queue isn't available on a personal account, so its two native paths are direct push and PR plus the merge API.
  • Placement. Local trunks are bare repos on the Mac Studio. Forgejo 16.0.5 runs on talos-jetson-2 on node-local disk, not Longhorn. GitHub is a private repo reached over the internet with SSH push. The forge rows measure the forge as the coordination point, which is exactly what the sequencer replaces. In the "as mirror" rows the forge only receives trunk.
  • Sequencer MVP. One process with a SQLite hash-chained log, footprints at target level from changed paths, derived and allocated files, commutative append, one CI run per batch, bisect on failure, and idempotent (change_id, rev). Not implemented: speculative execution of the next batch, Raft replication, read-set footprints, and footprint learning.
  • The sequencer runs CI twice per change at low load. The agent pre-tests and the batch is tested again, so one agent lands at half the rate of rebase-retest-push. The evidence carry-forward rule (skip the retest when nothing that change affects has moved) would fix it, but it isn't implemented in the MVP.
  • CI cost is fixed per run. A batch of 16 changes is tested in the same s as a single change. Real batch CI costs more, because more tests are affected, so the real gain is smaller than shown. The CI-runs-per-landing chart is the cost model to adjust.
  • Repetitions. Two per point for local configurations, one for Forgejo and GitHub. GitHub ran smaller (N ≤ 16, K = 2) to stay inside a bounded load; per-landing metrics normalize for that. A single repetition on a shared network is noisy, so read the GitHub points as indicative.
  • The Cloudflare sequencer. The Rust Trunk Durable Object (workers-rs 0.8.7) runs twice. Live (Cloudflare panel): the deployed Worker, with the trunk and every agent's fork as Artifacts repos; the Durable Object mints its own trunk write token, and each agent gets a fork it can write and a trunk token it can only read. Local (aqua circles on the Forgejo panel, faded on the Cloudflare panel): the same code under local workerd, with Forgejo standing in for Artifacts, so it compares directly with Forgejo push and PR-merge on the same host. Agents don't run CI themselves; only the sequencer's batch run counts, which is why CI runs per landing drop below 1. The "agents also pre-test" controls at 16 agents are in the correctness and run tables. Compare-and-swap on push was confirmed on both hosts; on Artifacts a stale old value is refused even when the push would fast-forward, and of 8 concurrent writers exactly one lands. Fetch errors in these rows are the bench's agents sharing one clone through worktrees (the lock race described above), not the sequencer. One repetition per point.
  • Review experiment. The corpus is small and hand-built (see the counts above), so treat the rates as a pilot. The reviewer prompt names the problem categories, as a real reviewer checklist would, and that primes the models. That's why clean changes are in the mix: they measure false alarms. Each reviewer ran once per change. The local model's output was capped at 1,024 tokens after one runaway generation. Claude ran through the Claude Code CLI with settings and tools disabled; Codex ran in an empty read-only directory. Both still load user-level instructions, if any exist. The mutation-testing threshold (0.70) was fixed before any defect results were seen. The review run overlapped the GitHub phase of the landing sweep.
  • Not measured. Semantic conflicts beyond migrations and lockfiles, real CI variance, and larger repos. The batching gain depends on the footprint distribution, which is assumed here, not measured from a real codebase.
